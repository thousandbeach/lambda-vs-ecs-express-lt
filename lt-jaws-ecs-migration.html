前回 LT のおさらい + なんで今これ?

前回ワイは、こう言いました。
「Lambda は API サーバーちゃう、ECS Express か Cloud Run でやれ」と。

ECS Express Mode は 2025 年 11 月 に AWS がやっと出した Cloud Run 対抗。
「使え」と言うた割に、世の中の実地検証はまだ少ない。
追い打ち: 2025/8〜 Lambda の INIT フェーズが課金対象に。 ウォーマー戦略のコスト前提が悪化し、 「Lambda は API サーバーちゃう」の根拠がもう一段強くなった。
念のため: このスライド配信、要件だけ見たら本来は S3 + CloudFront 一発が正解。 でも前回 Lambda に "あえて" 乗せた メタ構造 のまま、 今回も "あえて" ECS Express に乗せる。 → LT 後、 主張通り S3 + CloudFront に着地済 (現在この URL がそれ)。
主題は静的配信の最適化ちゃう、 API サーバー用途で Lambda vs ECS Express の殴り合い。
▶ そこで今日は、実地で殴り合った結果 を持ってきました。

    そもそも、ECS EXPRESS MODE とは

    必要なん、たった 3 つ。

    01
    コンテナイメージ
    ECR にあれば OK。今回は CDK の DockerImageAsset で自動 push。
    02
    Task Execution Role
    trust: ecs-tasks.amazonaws.com
    policy: AmazonECSTaskExecutionRolePolicy
    03
    Infrastructure Role
    trust: ecs.amazonaws.com
    policy: AmazonECSInfrastructureRoleforExpressGatewayServices
    その引き換えに ECS が裏で 全部やってくれる:
    Application Load Balancer / ACM 証明書 / Auto Scaling / 5XX 自動ロールバック / カナリアデプロイ / 共有 ALB(最大 25 サービス) / https://<serviceName-prefix>-<hash>.ecs.<region>.on.aws/ の自動発行。
    — Lambda Function URL の純ランダム文字列より prefix で識別しやすいのが地味に効く (例: lt-16808a31... と gxyrfra7u7zs7bz3...)。

    実測。数字で殴られる側になる番。

    // oha · 並列 50 · 30 秒 · GET /health · ap-northeast-1 から ap-northeast-1 へ
    // (主題: API サーバー用途の素の応答性能。 静的配信なら本来 S3+CloudFront 一択)
    Lambda (前回)ECS Express (今回)
    RPS (req/s)1,9072,734
    P50 (ms)25.215.3
    P90 (ms)29.824.7
    P95 (ms)31.930.6
    P99 (ms)38.175.3
    P99.9 (ms)127.4198.1
    Cold start (初回 ms)821230 (DNS+TLS のみ)
    結論: ECS が sustained throughput と中央値で勝ち (1.4 倍 RPS / P50 が 40% 速い)。 ただし、P99 は意外にも Lambda が勝つ (38ms vs 75ms)。 Warm な fan-out が効いて Lambda の tail が締まる、というのは事前予想と違った。
    静的配信の差は微妙。差が劇的になるのは I/O バウンドな API の局面、ということが実測でも示唆される結果。

    09 / 11

    移行体験ログ: 踏み抜いた落とし穴 6 連発。

    // 01 · CDK L2 未提供
    CfnExpressGatewayService のみ。
    cluster ARN を string で渡したり、cpu/memory を '256' と文字列で書いたりする。
    // 02 · Docker build context が無限再帰
    build context = repo root にしたら、ecs-app/cdk.out/ が context に取り込まれて
    .dockerignore 必須。CDK の staging dest 自体が context 内にできる。
    // 03 · SG description の許可文字
    'ALB → task' ❌ /
    'ALB -> task' も ❌ (`>` 不可)
    'ALB to task' ✅
    許可: a-zA-Z0-9. _-:/()#,@[]+=&;{}!$* のみ
    // 04 · タグ値の括弧禁止
    PreviousStep: 'lambda (cdk-app)' ❌
    カッコ・角括弧は AWS タグ値で弾かれる。'lambda-cdk-app' に変更。
    // 05 · cluster は ARN ちゃう、名前で渡せ
    CFN docs は「short name or full ARN」って書いてあるけど、modern ARN
    (arn:aws:ecs:.../cluster/<name>) を渡すと "Unexpected number of separators" で弾かれる。
    → cluster.clusterName でないと通らん。
    // 06 · URL は serviceName から決まらん
    docs は <serviceName>.ecs.<region>.on.aws って書いてあるけど、実測は <prefix>-<32hex>.ecs.<region>.on.aws。
    結局 Lambda Function URL と同じ 2-pass デプロイ。

    — 新機能あるある。L2 が来る頃には大半が消える。Issue aws/aws-cdk#36234 で L2 要望中。
